# ADR-003 — Modular Monolith 채택

- **상태**: Accepted
- **일자**: 2026-04-19
- **관련**: ARCH v0.1 §2, 개발 공수 제약

## 맥락
Beelink 단일 머신에서 `finance`, `tax`, `openclaw-sync`, `notification` 기능을 제공해야 한다. 각 기능을 독립 서비스(MSA)로 나누면 배포·모니터링·디버깅 부담이 커지지만, 단일 모놀리스는 모듈 경계가 흐려져 Phase 2 확장을 저해할 수 있다.

## 결정
**단일 Node.js(Fastify) 프로세스 내에서 모듈 경계를 엄격히 유지하는 Modular Monolith**를 채택한다.
- 모듈 간 호출은 함수 레벨 import만 허용 (HTTP·큐 경유 금지)
- 순환 의존은 CI에서 `madge --circular`로 차단
- 각 모듈은 자체 타입/DTO를 소유, 공용 레이어(`crypto`, `http/gateway`)만 공유
- 훗날 모듈을 독립 서비스로 분리할 때 경계가 이미 명확하도록 설계

## 결과
**긍정**
- 배포/로그/모니터링 단일화 → 주 5시간 예산에 적합
- 트랜잭션 경계가 하나의 DB 연결 안에 존재 → 일관성 쉬움
- 인메모리 호출로 성능 최적

**부정 / 비용**
- 한 모듈 장애가 전체 프로세스에 영향 → Fastify plugin 격리 + `undici` 타임아웃으로 완화
- 개발자 규율 의존 (모듈 경계 준수)

## 대안
1. **MSA (컨테이너 N개)**: 단일 개발자에게 운영 부담 과잉.
2. **Serverless Functions**: 로컬 Beelink 환경과 부적합, 콜드스타트.
3. **단일 스크립트(계층 구분 無)**: Phase 2 확장 시 재작성 부담.
